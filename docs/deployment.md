# Static Site Deployment and Rollback

## Target and Release Paths

The site is served at `https://billybitcoin.cloud/robot-arm/` from `/var/www/billybitcoin.cloud/html/robot-arm/` on `billy@helios`. Deploy only this directory. Publishing the static bundle needs no Nginx restart, container rebuild, database migration, or robot firmware update.

The normal path is `.github/workflows/deploy.yml` after successful push CI on `main`. It downloads that CI run's tested `robot-arm-site-dist` artifact, checks for superseded revisions when preparing the release, and deploys through the production GitHub Environment. Environment protection rules are configured in GitHub, not enforced by an extra prompt in the workflow YAML.

Manual `workflow_dispatch` defaults `dry_run` to true and rebuilds the site, including CAD exports. It does not run the full CI tests itself. A deploy workflow retains its uploaded site artifact while GitHub artifact retention permits it; do not treat it as a permanent backup.

## GitHub Environment

The `production` environment needs these secret names:

- `HELIOS_HOST`: Helios's Tailscale hostname or address, with no whitespace.
- `HELIOS_USER`: SSH username only, such as `billy`; no host, `@`, colon, or whitespace.
- `HELIOS_SSH_KEY`: deployment SSH private key.
- `TS_AUTHKEY`: reusable Tailscale auth key used to join the Actions runner to the tailnet.

Authorized operators can configure the environment through GitHub or `gh secret set NAME --repo hollowc2/robot-arm-build-lab --env production`. Do not print secret values or commit them to the repository.

A green CI run does not mean production changed. Check the deploy job separately. During the factory rollout the Actions Tailscale join failed with an invalid-key error, and the site was published through the existing working SSH connection instead. That failure is a deployment credential issue, not a reason to alter application code or bypass tests. Recheck the current job before assuming the credential has been repaired. Credential renewal is a separate operation.

## Direct SSH Fallback

Use this path only for an explicitly authorized release. Work from the repository root on the exact commit being released, with a clean source tree and validated CAD web assets. Run the build, motion checks, and desktop/mobile browser checks first:

```bash
npm --prefix site ci
npm --prefix site run build
npm --prefix site run test:motion
npm --prefix site run smoke -- --workers=1
```

Install the Playwright browser if needed, as described in [the README](../README.md#local-site). Reuse validated meshes for a site-only edit; regenerate exports when CAD or export inputs change.

Before a live write, confirm SSH reaches Helios, Nginx is healthy, disk space is sufficient, the target directory is correct, and the current public route responds. Record the current release marker if present and the index checksum. Record a rollback archive outside the public web root. For example, using the existing SSH account:

```bash
release_sha=$(git rev-parse HEAD)
release_stamp=$(date -u +%Y%m%dT%H%M%SZ)
backup_file="/home/billy/robot-arm-releases/robot-arm-before-${release_stamp}.tar.gz"

ssh -F /dev/null -o BatchMode=yes -o ConnectTimeout=10 billy@helios \
  "mkdir -p /home/billy/robot-arm-releases && tar -czf '$backup_file' -C /var/www/billybitcoin.cloud/html/robot-arm . && sha256sum /var/www/billybitcoin.cloud/html/robot-arm/index.html"
```

Keep the exact archive path and baseline checksum in the release record. Do not overwrite an earlier archive.

The direct releases used a small optional `release.json` in `site/dist/` to identify the deployed source commit. It is not generated by Vite or the Actions workflow. If using it, generate it **after** the build, which clears `site/dist/`:

```bash
python3 - <<'PY'
import json
import subprocess
from pathlib import Path

commit = subprocess.check_output(["git", "rev-parse", "HEAD"], text=True).strip()
Path("site/dist/release.json").write_text(json.dumps({
    "commit": commit,
    "demo": "sorting-factory",
    "controls": ["Factory", "Joints"],
}) + "\n")
PY
```

Upload assets before switching the entry page. Preserve old hashed assets until rollback is no longer needed. The direct fallback intentionally does not use `--delete`; the existing Actions workflow does use `--delete` when syncing its complete artifact.

```bash
rsync --archive --compress --exclude=index.html --exclude=release.json \
  -e 'ssh -F /dev/null -o BatchMode=yes -o ConnectTimeout=10' \
  site/dist/ billy@helios:/var/www/billybitcoin.cloud/html/robot-arm/

scp -F /dev/null -o BatchMode=yes -o ConnectTimeout=10 \
  site/dist/index.html \
  billy@helios:/var/www/billybitcoin.cloud/html/robot-arm/.index-next.html
scp -F /dev/null -o BatchMode=yes -o ConnectTimeout=10 \
  site/dist/release.json \
  billy@helios:/var/www/billybitcoin.cloud/html/robot-arm/.release-next.json

ssh -F /dev/null -o BatchMode=yes -o ConnectTimeout=10 billy@helios \
  'mv /var/www/billybitcoin.cloud/html/robot-arm/.index-next.html /var/www/billybitcoin.cloud/html/robot-arm/index.html && mv /var/www/billybitcoin.cloud/html/robot-arm/.release-next.json /var/www/billybitcoin.cloud/html/robot-arm/release.json'
```

Each rename atomically replaces that file. Index and release-marker replacement are two separate operations; the release marker is diagnostic, not a transaction mechanism. The rsync exclusions also skip nested `index.html` files, so this fallback assumes the existing `/robot-arm/simulator/` redirect is already installed. If changing that redirect, explicitly include its updated file in the release plan.

For browser validation before activation, upload the candidate entry page under an ordinary name such as `factory-review.html` in the same directory. Its absolute `/robot-arm/` asset paths still point at the staged assets. Do not use a dot-prefixed filename for a browser review URL: the current Nginx rules do not serve those files. After validation, rename the candidate into `index.html`.

## Validation

Check service health, verify the deployed index checksum matches `site/dist/index.html`, and verify the optional release marker identifies the intended commit. Then check the public page:

- Factory and Joints are the only tabs; no Build panel, structure selector, or architectural presets appear.
- All CAD meshes load, the factory starts, and a complete batch delivers six blocks, two per color.
- Shuffle, pause/resume, and manual takeover work. Reduced-motion startup waits for Start sorting.
- No browser exceptions, missing scripts, missing styles, or missing model assets occur. Check mobile behavior as well as desktop.

During the removal rollout, public connections intermittently timed out. Diagnose connection failures separately from missing assets or application errors. Nginx binds specific addresses, so a failed request to `127.0.0.1:80` or `127.0.0.1:443` does not establish that the site is down. Inspect the existing listener configuration before probing it. A temporary browser resolver override to a verified listener can isolate DNS/address-selection issues without changing DNS, Nginx, firewall rules, or site exposure. Record when that route was used; also confirm the canonical URL serves the intended page.

## Rollback

If release validation fails, restore the recorded baseline before further live debugging. With the exact `backup_file` recorded above:

```bash
ssh -F /dev/null -o BatchMode=yes -o ConnectTimeout=10 billy@helios \
  "tar -xzf '$backup_file' -C /var/www/billybitcoin.cloud/html/robot-arm && systemctl is-active nginx"
```

Then verify the baseline index checksum, release marker if it existed, and public behavior. This overlay restores the previous files while leaving any newly uploaded hashed assets unreferenced; no broad deletion or service restart is needed. If the baseline had no release marker, account for a newly added marker separately so it cannot be mistaken for the restored release. Keep a record of the intended commit, backup path, validation results, and whether rollback was used.
